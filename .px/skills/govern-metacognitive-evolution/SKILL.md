# Govern Metacognitive Evolution

Keep this skill lazy. Load `references/capability-index.json` only after this
domain is selected, then load exactly one referenced contract. Load
`references/orchestration-index.json` only when several contracts must compose.

## Workflow

1. Bind the request to one project, task class, evidence scope, and time boundary.
2. Separate observations, inferences, assumptions, unknowns, disputes, and policy choices.
3. Select one declared capability and inspect its semantic effects, dependencies, formulas, and failure modes.
4. Use a read-only runtime operation first; declare and authorize any later mutation through the existing execution contract.
5. Preserve existing evidence, graph, memory, routing, improvement, and certification owners.
6. Test alternatives, negative cases, calibration, rollback, and held-out behavior.
7. Emit component values, provenance, residual uncertainty, and revocation triggers.

## Hard boundaries

- Never request, infer, record, or expose private chain-of-thought. Reconstruct only declared operational events, evidence links, decisions, alternatives, and outcomes.
- Never infer personality, intelligence, IQ, protected traits, health, employability, or psychological state. Engineering-DNA records describe observable repository and workflow practices only.
- Similar names, trees, or embeddings do not prove behavioral equivalence and never authorize deletion or supersession.
- Capability mutation and self-improvement remain proposal-only until independently tested, approved, rollback-ready, and admitted by existing owners.
- "Knowledge physics" is an auditable operational metaphor. Expose trust, age, contradiction, volatility, connectivity, and validation components; never treat a composite score as hidden authority.
- Use the existing project memory, evidence ledger, capability graphs, recovery coordinator, and revocable certification system. Do not create parallel canonical stores.
