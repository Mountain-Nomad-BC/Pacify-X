# PX Lean Engineering

1. Trace the actual runtime flow, callers, contracts, effects, and acceptance criteria.
2. Decide whether the requested capability needs to exist.
3. Query the project map, symbols, graph, memory, skills, tools, workflows, and prior validated outcomes for an existing owner.
4. Prefer, in order: an existing owner; standard/platform capability; installed dependency; one shared root-cause change; the minimum genuinely new component.
5. Record the before/after delta for files, dependencies, services, configuration, schemas, tables, and abstractions.
6. Explain why any new owner is necessary and how it is bounded, cancelled, receipted, recovered, and removed.
7. Leave at least one bounded runnable check for non-trivial logic and run affected mandatory certification.
8. Record deliberate simplification debt with a ceiling, owner, trigger, and revisit condition.

Never minimize away trust-boundary validation, data-loss protection, security, permissions, accessibility, project isolation, evidence, rollback/recovery, real hardware tuning, or user-explicit behavior.

Return the reused owners considered, chosen approach, measured delta, tests/evidence, residual risk, and any bounded debt. Do not claim unmeasured complexity or cost savings.
