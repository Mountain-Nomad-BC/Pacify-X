# SBOM Policy

Pacify-X produces a Software Bill of Materials for every public release, so a consumer can answer
"what exactly is in this artifact?" without trusting a summary.

---

## 1. Format

- **CycloneDX JSON** is the primary format (widely supported, good tooling, rich component
  metadata).
- **SPDX** is acceptable as an alternative where a toolchain prefers it.
- The chosen format is recorded in the release manifest so consumers know what they are reading.

## 2. Scope

The SBOM covers every artifact that is actually shipped:

| Artifact | In SBOM |
|---|---|
| Python package and its runtime dependencies | yes |
| VSIX and its bundled npm dependencies | yes |
| Embedded/embeddable Python runtime and its components | yes |
| Vendored or embedded third-party source | yes |
| Local model runtime (llama.cpp) | **no** — built locally by the operator, not distributed; its identity is recorded in the runtime lock instead |
| Model weights (GGUF) | **no** — supplied by the operator, not distributed; identity recorded at admission |
| CUDA toolkit | **no** — operator-installed; operator responsibility |

The distinction is deliberate: an SBOM describes **what Pacify-X distributes**. Components the
operator obtains independently are recorded as provenance, not as Pacify-X-distributed
components — claiming them in an SBOM would misrepresent the supply chain.

## 3. Required component fields

For each component:

- name and version (exact, pinned);
- package URL (purl) where available;
- licence (SPDX identifier where determinable);
- source (repository / registry);
- hash where available;
- relationship (`direct` / `transitive`, and the dependency it comes from).

## 4. Generation

- The SBOM is generated **before the freeze**, from the **actual resolved dependency set** — not
  from a hand-maintained list.
- It is generated by a scripted, deterministic process so a second run produces the same SBOM
  except for an explicitly recorded timestamp.
- It is bound to the release identity: the same commit, tag, and artifact hashes.

Generating an SBOM, a notice bundle, or a provenance document **after** certification would
change the release state and invalidate the certification. They are therefore part of the
pre-freeze generation set.

## 5. Storage and publication

- The SBOM is published with the release alongside checksums.
- It is retained as release evidence.
- It is not rewritten after publication; a corrected SBOM accompanies a new release and the
  discrepancy is recorded.

## 6. Verification

A consumer should be able to:

1. obtain the SBOM;
2. confirm the artifact hash matches the published checksum;
3. confirm every component in the SBOM corresponds to a component in the shipped artifact;
4. confirm no shipped component is missing from the SBOM.

Step 3 and 4 are the ones that matter — an SBOM that omits a shipped component is worse than no
SBOM, because it creates false confidence.

## 7. Current status

| Item | Status |
|---|---|
| Policy | **this document** |
| Format decision | CycloneDX JSON primary |
| Generator | **not yet implemented** — repair item (WS-6) |
| Release gate check | declared in `docs/compliance/RELEASE_COMPLIANCE_CHECKLIST.md`; enforced once the generator exists |

Reported plainly: the policy and gate are defined; the generator is a required repair item.
An SBOM must not be hand-written to satisfy the gate, because a hand-written SBOM is exactly the
false confidence this policy exists to prevent.
